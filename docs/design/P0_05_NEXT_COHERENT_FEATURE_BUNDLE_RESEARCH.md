# P0-05 下一组连贯功能包研究

## 1. 研究结论

推荐下一实现轮使用暂定名称：

`P0-05A_RUNTIME_BUILDING_LIFECYCLE_AND_SAFE_REMOVAL`

主题严格限定为：

```text
统一一份运行时建筑记录
→ 详情面板读取该记录
→ 发起“移除建筑（原型）”
→ 明确确认或取消
→ 确认后同步清理节点、选择和占用格
→ 原位置可以重新建造
```

推荐的是“运行时建筑生命周期基础 + 带确认的安全移除原型”，不是正式拆除系统。它不包含资源返还、施工时间、耐久、升级、道路、生产、存档或正式建筑定义。

本文件只研究和设计，不实现任何功能。

用户已经接受本研究的实现分叉：

- 操作入口使用“移除建筑（原型）”；
- 点击入口只进入同面板确认状态，确认前可以取消；
- 确认后立即移除，不实现 undo；
- “原位重建”只表示释放的格子可以通过既有建造流程再次放置，不增加重建、恢复或撤销按钮；
- `ConstructionController` 是运行时建筑记录的唯一权威；
- 选择状态以 `selected_placement_id` 为权威，不以 Node2D 引用为权威；
- 建筑节点 metadata 只保留 `placement_id`，作为视觉节点与权威记录之间的身份桥；
- 不需要先做 Figma，继续复用现有 280 x 360 详情面板。

## 3. 当前代码和数据边界

### 3.1 当前建筑状态分布

`ConstructionController` 目前同时维护：

- `placements: Array[Dictionary]`；
- `occupied_cells: Dictionary`；
- `_next_placement_id`；
- `PlacedBuildings` 下的运行时 Node2D。

每个建筑节点还通过 metadata 保存：

- `placement_id`；
- `origin_cell`；
- `footprint_cells`；
- `selection_bounds`；
- `display_name`；
- `building_type`；
- `prototype_status`。

`BuildingSelectionController` 直接从节点 metadata 读取详情字段，建造控制器则从 `placements` 和 `occupied_cells` 判断放置状态。

当前切片中这些数据一致，但如果直接增加拆除、道路或升级，三个表达面很容易分叉：

1. 记录删除了但节点仍存在；
2. 节点删除了但占用格没有释放；
3. 面板显示的 metadata 与逻辑记录不同；
4. placement id 被错误复用；
5. 选择仍指向已经移除的建筑。

P0-04B 已补上节点离开场景时清除选择引用，但尚未定义谁是建筑运行时数据的唯一权威。

### 3.2 当前交互边界

输入仍由 `BlankMapRoot._input` 统一路由：

- idle：左／中／右候选拖动、左键单击选择、滚轮缩放、Esc 清除选择；
- placing：左键确认、中键拖动、滚轮缩放、右键或 Esc 取消；
- 详情面板可见时，其矩形阻止鼠标和滚轮穿透。

下一功能包不能增加第二个 `_input`、每栋建筑独立输入或第二套坐标转换。

## 4. 路线图中的真实下一阶段

仓库当前没有独立 README、roadmap、DECISIONS、CHANGELOG 或 handoff 文件，也没有冻结的 P0-05 编号。

现有设计文档明确的依赖顺序是：

```text
地图导航
→ 固定 UI Shell
→ 网格建造
→ 建筑选择与详情
→ 后续建筑、道路或存档能力
```

但“后续具体先做什么”尚未冻结。因此不存在必须机械执行的既定道路或拆除阶段。

从当前实现依赖看，下一阶段应先解决建筑记录、节点、选择与占用格的一致性。否则建造体验、道路和任何正式属性都会依赖一份尚未明确的临时数据源。

## 5. 三个候选方向比较

| 维度 | A. 建筑生命周期基础 | B. 建造体验扩展 | C. 地图与建筑基础规则 |
|---|---|---|---|
| 当前 P0 匹配度 | 高 | 中高 | 中 |
| 冻结设计 | 部分：已有 placement id、网格、选择 | 部分：已有连续放置和失败原因 | 低：道路和启用规则未冻结 |
| 玩家闭环 | 选中→确认移除→释放→重建 | 选择模板→连续建造→反馈 | 铺路／连接→启用建筑 |
| 数据模型风险 | 可主动降低 | 会继续依赖当前分散数据 | 会过早固化道路与建筑规则 |
| 一次实体测试 | 适合，约 16 项 | 适合，但价值主要是操作便利 | 难，需先确认规则和地图表达 |
| 高风险系统数量 | 1：生命周期一致性 | 1：建造交互扩展 | 至少 2：道路拓扑＋建筑启用 |
| 自动覆盖程度 | 高 | 高 | 中，需要更多空间规则 |
| 回滚难度 | 低到中 | 低 | 中高 |
| 对正式建筑／存档耦合 | 可保持 P0 内存态 | 中 | 高 |
| 是否需要先做 Figma | 否 | 可能需要正式建造菜单时再做 | 大概率需要地图规则和视觉研究 |

### 5.1 A：建筑生命周期基础

优势：

- 直接修复当前最明显的数据一致性风险；
- 为以后拆除、升级、资源、道路启用和存档提供唯一 placement id 与查询入口；
- 可以形成完整的玩家闭环；
- 清理占用格、节点和选择均可精确自动测试；
- 不要求正式建筑目录或持久化 schema。

风险：

- 如果把 P0 运行时记录误写成正式存档模型，会造成过早承诺；
- “删除后能否撤销”会改变状态和 UI 范围；用户已确认本轮不实现；
- 必须保证只释放属于目标 placement id 的格子。

### 5.2 B：建造体验扩展

可能内容包括模板重复选择、更细失败原因和放置反馈。

暂不优先的原因：

- 当前已支持连续建造、有效／无效预览和简短失败原因；
- 它提高操作便利，但没有解决数据分散；
- 若先增加多个模板，metadata、placements 和占用表的重复会扩大；
- 正式建造菜单的信息架构尚未设计，继续加入口可能重新造成 UI 混乱。

等运行时建筑记录统一后，再做多模板或更完整建造入口成本更低。

### 5.3 C：地图与建筑基础规则

可能内容包括道路连接、启用／未启用和道路占地协调。

暂不优先的原因：

- 仓库没有冻结道路拓扑、道路建造方式或建筑入口规则；
- 现有道路只是灰盒视觉，不是逻辑网格；
- 同时引入道路连接和建筑启用至少包含两个高风险系统；
- 容易把当前 40 单位原型格和静态道路错误固化成正式城市规则；
- 需要先进行地图规则研究，可能还需要 Figma 或地图视觉方案。

## 6. 推荐方向及依据

推荐 A：**建筑生命周期基础**。

但建议把下一轮严格实现为：

`统一运行时记录 + 带明确确认／取消的测试建筑移除`

现在做它的原因：

1. 当前每栋建筑已经有稳定的 placement id、网格原点和 footprint。
2. P0-04B 已经验证选择、详情面板与节点退出安全清理。
3. `occupied_cells` 已按 placement id 保存，具备精确释放条件。
4. 详情面板已有空余区域，可放置少量真实可用操作，不需要新页面。
5. 删除后原位置重新建造能形成一次清晰、可观察的闭环。
6. 它先建立后续所有建筑能力都需要的一致性合同。

暂不做 B，是因为当前建造闭环已经可用，继续扩展会放大临时数据重复。

暂不做 C，是因为道路和启用规则没有冻结，且会一次引入两个高风险系统。

## 7. 下一实现轮目标

```text
放置测试建筑
→ 退出建造
```

## 8. 建议的唯一运行时记录

P0 阶段不创建正式 Resource、数据库或存档 schema。

推荐由现有 `ConstructionController` 继续作为唯一运行时权威，维护：

```text
building_records_by_id
placement_order
occupied_cells
next_placement_id
```

每条记录只包含当前闭环必需字段：

- `placement_id: int`
- `template_id: StringName`，固定为测试模板
- `display_name: String`
- `building_type: String`
- `origin_cell: Vector2i`
- `footprint: Vector2i`
- `occupied_footprint_cells: Array[Vector2i]`
- `selection_bounds: Rect2`
- `lifecycle_state`，当前只允许 `RUNNING`
- `node: Node2D`

约束：

- 记录是面板与生命周期操作的唯一业务数据源；
- 建筑节点只保留 `placement_id` metadata，命中边界也从权威记录读取；
- `occupied_cells[cell] = placement_id` 继续作为空间索引；
- 不在选择控制器中复制 40、3、2 或正式属性；
- 选择控制器只保存 `selected_placement_id`，需要节点或字段时向建造控制器查询；
- placement id 单调递增，删除后不复用；
- 该字典是 P0 运行时结构，不承诺未来存档兼容。

不建议本轮新增独立 `BuildingRegistry` 脚本。当前只有一个测试模板和一个建造控制器，拆成第二个数据服务会增加连接和生命周期复杂度。正式多城市或存档研究时再评估提取。

## 9. 建议状态模型

选择控制器增加一个有限状态：

```text
NONE
SELECTED
REMOVE_CONFIRM
```

规则：

- `NONE`：没有选中建筑，面板隐藏；
- `SELECTED`：显示详情和一个真实可用的“移除建筑（原型）”入口；
- `REMOVE_CONFIRM`：同一面板显示简短警示、确认与取消按钮；
- 取消确认：回到 `SELECTED`，记录、节点和占用不变；
- 确认移除：调用 ConstructionController 的单一移除 API；
- 移除成功：进入 `NONE`，隐藏面板和描边；
- 建筑被外部移出场景：安全进入 `NONE`；
- 进入 placing：无论当前是 `SELECTED` 还是 `REMOVE_CONFIRM` 都清除选择；
- 不增加全局通用状态机。

## 10. 输入所有权

- `map_pan_controller.gd` 继续是唯一 `_input`。
- `BuildingSelectionController` 继续不实现 `_input`。
- 移除、确认和取消使用详情面板 Button signal。
- 面板区域继续由现有动态 rect 阻止地图输入穿透。
- idle Esc：
  - `REMOVE_CONFIRM` 时建议先取消确认并回到 `SELECTED`；
  - `SELECTED` 时清除选择。
- 空白地图单击在任何选择状态下清除选择并取消确认。
- 拖动和缩放保留 `SELECTED`；在 `REMOVE_CONFIRM` 下也建议保持确认界面，避免导航时状态突然改变。
- 进入 placing 取消任何待确认移除，不恢复旧选择。
- 同一点击不能同时确认移除、选择建筑或开始地图拖动。

## 11. 安全移除合同

建议唯一 API：

```text
remove_placed_building(placement_id) -> bool
```

必须按以下顺序保证一致性：

1. 查询权威记录，不存在则返回 false，且不改变任何状态；
2. 验证记录指向当前运行时建筑；
3. 遍历记录 footprint；
4. 只删除 `occupied_cells[cell] == placement_id` 的项；
5. 从权威记录和顺序索引删除 placement；
6. 使选择控制器清除所选引用和 UI；
7. 释放对应建筑节点；
8. 返回 true。

同一节点若意外 `tree_exited`，也必须通过 `placement_id` 进行幂等同步清理：释放仍归该 id 所有的占用格、移除权威记录和顺序索引，并通知选择控制器清除同 id 的选择。显式移除后再次收到 `tree_exited` 不得造成二次删除或释放其他建筑的占用格。

失败不得部分清理。若记录与占用表不一致，测试环境应暴露错误并停止，不做静默“尽量删除”。

本轮不实现资源返还、拆除时间、动画、废墟、恢复建筑或批量移除。

## 16. 自动验收标准

下一轮建议 16 项核心自动验收：

1. 主场景、脚本和资源无加载错误。
2. 仍只有一个 MapWorld、Camera2D、UI Shell 和 `_input`。
3. 成功放置创建一条权威记录、一个节点和六个同 placement id 占用格。
4. placement id 单调递增，移除后不复用。
5. 详情面板字段全部来自权威记录。
6. 选择控制器不再依赖重复的业务 metadata。
7. 点击移除入口只进入 `REMOVE_CONFIRM`，不会立即删除。
8. 取消确认恢复 `SELECTED`，节点、记录和占用均不变。
9. Esc 在 `REMOVE_CONFIRM` 只取消确认并保留选择。
10. 确认移除删除准确的一条记录和对应节点。
11. 确认移除只释放值等于目标 placement id 的六个占用格。
12. 移除一栋建筑不影响其他建筑、记录或占用格。
13. 移除后选择、描边和详情面板全部清除。
14. 移除后原 footprint 可以重新成功建造。
15. 进入 placing 会取消待确认状态，placing 左键不会触发移除或选择。
16. 原 construction smoke、selection smoke 和 `git diff --check` 全部继续通过。

辅助断言还应覆盖不存在 placement id 返回 false、重复确认不产生二次变化，以及面板按钮不穿透地图。

## 17. 用户实体测试清单

下一轮建议一次完成 16 项实体测试：

1. 放置两栋测试建筑并退出建造。
2. 选择第一栋，详情字段正常。
3. 点击“移除建筑（原型）”只出现确认状态，建筑仍存在。
4. 点击取消后返回原详情，建筑仍可选。
5. 再次进入确认，按 Esc 返回原详情。
6. 进入确认后拖动地图，建筑、描边和确认面板保持正确。
7. 进入确认后滚轮缩放，描边仍对齐且面板固定。
8. 确认面板内滚轮和拖动不穿透地图。
9. 点击确认后目标建筑消失。
10. 确认后描边和详情面板消失。
11. 第二栋建筑仍存在且可以选择。
12. 原目标位置不再显示“位置已占用”。
13. 在原位置重新放置测试建筑成功。
14. 新建筑获得新的 placement id 表现，不与旧选择混淆。
15. 在移除确认状态点击建造入口，确认状态清除且建造预览正常。
16. 完整流程后地图拖动、滚轮缩放和重复占用拒绝仍正常。

用户无需测试资源返还、拆除时间、道路、升级、生产或存档，因为这些均不在范围内。

## 18. 风险和失败路径

### 18.1 数据源仍然重复

风险：为兼容旧测试同时保留 placements、完整 metadata 和新 registry。

停止方式：若面板或移除逻辑仍需在两个业务数据源之间猜测，停止实现并重新收敛权威记录。

### 18.2 部分清理

风险：节点删除但 occupied_cells 未释放，或释放了其他建筑的格子。

停止方式：移除 API 必须在变更前验证记录和 ownership；任何不一致由自动测试阻断提交。

### 18.3 输入穿透

风险：点击确认按钮同时触发地图选择或拖动。

停止方式：复用面板实际 global rect 和 GUI signal，不在按钮脚本中新增 `_input`。

### 18.4 过早正式化

风险：把 P0 字典当作永久存档 schema。

停止方式：文档和代码命名明确使用 runtime/prototype，不加入版本号、序列化或迁移层。

### 18.5 删除后撤销分叉

风险：若同时要求“释放格子可重建”和“随时撤销删除”，必须处理新建筑占用原位置后的冲突。

停止方式：下一轮只实现确认前可取消；确认后的 undo 另行研究，不能顺手加入。
